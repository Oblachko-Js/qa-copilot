# Подходы к оценке критериев

Оценивать ответы следует на одном и том же фиксированном наборе требований и по шкалам из документа [«Критерии оценки AI-системы»](kriterii-otsenki-ai-sistemy.md). Для каждого ответа сохраняются исходное требование, результат генерации, оценка и, для экспертных методов, краткое обоснование. Это позволит сравнивать результаты разных запусков и моделей на одинаковом основании.

## 1. Валидность JSON-схемы — автоматическая проверка Pydantic

**Метод:** каждый ответ проверяется по `TestCaseList` и вложенной схеме `TestCase`. Фиксируется, прошёл ли ответ разбор без ошибки и соблюдены ли ограничения схемы. Для набора требований рассчитывается доля успешно прошедших проверку ответов.

**Почему этот метод подходит:** валидность — формальное свойство контракта API. Обязательные поля, типы, допустимые приоритеты и ограничения количества кейсов можно проверить детерминированно. LLM-оценщик здесь не нужен и мог бы дать нестабильный результат.

## 2. Покрытие сценариев — сравнение с эталонным списком

**Метод:** для каждого требования заранее составляется эталонный список значимых сценариев. Сгенерированные кейсы сравниваются с ним; для каждого эталонного сценария отмечается, покрыт ли он хотя бы одним кейсом. Рассчитывается доля покрытых сценариев. Эталон размечается вручную; сопоставление можно выполнять вручную или с помощью LLM-оценщика с последующей проверкой спорных совпадений.

**Почему этот метод подходит:** без внешнего эталона нельзя объективно определить, какие риски требования являются значимыми и что считать достаточным покрытием. Эталон позволяет сравнивать ответы между собой, а не только оценивать их общее впечатление.

## 3. Отсутствие галлюцинаций — LLM-оценщик с проверяемым обоснованием

**Метод:** LLM-оценщику передаются исходное требование и один тест-кейс. Он определяет, подтверждаются ли требованием предусловия, шаги и ожидаемый результат, и отмечает неподтверждённые или противоречащие детали. Для каждого замечания оценщик должен привести фрагмент тест-кейса и объяснить, почему он не следует из требования. По кейсам рассчитывается доля ответов без неподтверждённых деталей.

**Почему этот метод подходит:** обнаружение выдуманной функциональности требует сопоставить смысл кейса со смыслом требования; проверка JSON или простые текстовые эвристики этого не выявляют. Обоснование делает оценку проверяемой человеком. Спорные срабатывания и часть остальных оценок следует перепроверять вручную, поскольку сам LLM-оценщик тоже может ошибиться.

## 4. Читаемость и готовность — ручная оценка с дополнительными эвристиками

**Метод:** QA-инженер оценивает небольшую репрезентативную выборку по шкале из документа с критериями и отмечает, можно ли использовать кейс без существенных правок. Дополнительно фиксируется время ревью. Эвристики — например, слишком длинные шаги или отсутствие глагола действия — используются как сигналы для просмотра, но не заменяют оценку человека.

**Почему этот метод подходит:** понятность и готовность зависят от того, как QA-инженер будет выполнять тест. Полная автоматизация этих оценок может пропустить неоднозначность или неверный ожидаемый результат. Эвристики полезны для поиска подозрительных кейсов, но сами по себе не доказывают их непригодность.

## 5. Адекватность приоритета — сравнение с экспертной разметкой

**Метод:** для эталонных сценариев эксперт заранее определяет ожидаемый приоритет. Приоритет сгенерированного кейса сопоставляется с приоритетом соответствующего эталонного сценария; рассчитывается доля совпадений. Несовпадения проверяются по исходному требованию и влиянию сценария.

**Почему этот метод подходит:** приоритет зависит от значимости риска, а не только от формата или наличия поля. Экспертная разметка задаёт единое основание сравнения, а разбор несовпадений показывает, недооценивает ли модель важные проверки или переоценивает малозначимые.

## Сводка

| Критерий | Основной метод | Тип проверки |
|---|---|---|
| Валидность схемы | Разбор по Pydantic-схеме | Автоматическая |
| Покрытие сценариев | Сравнение с эталонными сценариями | Ручная разметка эталона; ручное или вспомогательное автоматизированное сопоставление |
| Отсутствие галлюцинаций | LLM-оценщик с обоснованием | Автоматизированная смысловая оценка и ручная проверка спорных результатов |
| Читаемость и готовность | Оценка QA-инженером, дополненная эвристиками | Человеческая оценка; эвристики только помогают отбирать случаи |
| Адекватность приоритета | Сравнение с экспертной разметкой приоритетов | Экспертная разметка и сравнение |

Этот документ описывает методы оценки. Проверочный набор требований, скрипт прогона и таблица результатов относятся к следующему пункту плана и здесь не создаются.
