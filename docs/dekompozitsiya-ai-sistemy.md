# Декомпозиция AI-системы для оценки

## Тема проекта

AI-ассистент для QA-инженера помогает выполнять рутинные задачи тестирования. Текущий прототип принимает текст требования и генерирует по нему тест-кейсы на русском языке. В дальнейшем проект можно расширить анализом багов и документации.

## Задачи системы

По входному требованию система должна:

1. Понять описание функции и ожидаемое поведение.
2. Выделить сценарии проверки: позитивные, негативные и граничные.
3. Сформулировать предусловия, шаги и ожидаемый результат для каждого сценария.
4. Назначить тест-кейсу приоритет.
5. Вернуть результат в согласованной JSON-структуре.

## Компоненты системы

| Компонент | Назначение | Текущее состояние |
|---|---|---|
| HTTP API на FastAPI | Принимает запрос и возвращает результат генерации | Реализованы `GET /health` и `POST /generate-testcases` |
| Валидация входного запроса | Проверяет требование, температуру и максимальное число кейсов | Реализована схемой `GenerateRequest`: температура от 0 до 2, число кейсов от 1 до 15 |
| Промпт | Передаёт модели требование и инструкции к ответу | Функция `build_prompt` просит писать по-русски и задаёт поля результата |
| Вызов LLM | Генерирует тест-кейсы с выбранной моделью и температурой | Используется OpenAI-совместимый API; адрес, ключ и модель задаются переменными окружения |
| Структурированный вывод | Ограничивает форму ответа и проверяет типы и обязательные поля | Используются Pydantic-схемы `TestCase` и `TestCaseList` и метод `chat.completions.parse` |
| Обработка ошибок | Возвращает понятный ответ при ошибке конфигурации или генерации | Для ошибок LLM и разбора ответа возвращается HTTP 502 |
| RAG-слой | В будущем добавит контекст из документации и истории багов | Пока не реализован; не входит в текущий прототип |

Текущий промпт просит составить краткий и полный набор тест-кейсов, но отдельно не требует явно помечать каждый кейс как позитивный, негативный или граничный. Это возможное направление улучшения промпта, а не уже реализованная функция.

## Части результата

Каждый тест-кейс содержит:

- `title` — заголовок;
- `preconditions` — предусловия;
- `steps` — последовательность шагов;
- `expected_result` — ожидаемый результат;
- `priority` — приоритет: `низкий`, `средний` или `высокий`.

Список кейсов возвращается в поле `test_cases`. Pydantic проверяет наличие обязательных полей, типы значений и допустимый диапазон числа кейсов. Ключи JSON оставлены стабильными и англоязычными, текстовые значения генерируются на русском.

## Поток обработки запроса

1. Пользователь отправляет в `POST /generate-testcases` текст требования, температуру и максимальное число кейсов.
2. FastAPI и Pydantic проверяют входные значения.
3. Приложение получает настройки провайдера и модели из переменных окружения.
4. Промпт вместе с требованием отправляется в LLM с заданной температурой и схемой `TestCaseList`.
5. Ответ разбирается и проверяется по Pydantic-схеме. Если кейсов больше заданного максимума, приложение оставляет только разрешённое количество.
6. API возвращает структурированный JSON либо понятную ошибку HTTP 502, если провайдер недоступен или ответ не удалось разобрать.

## Что оценивается

Формат JSON и соответствие Pydantic-схеме проверяются автоматически при разборе ответа. Основные объекты оценки — качество содержания:

- **Покрытие рисков требования:** отражает ли набор кейсов значимые сценарии, включая позитивные, негативные и граничные.
- **Отсутствие выдуманной функциональности:** не добавляет ли модель требования, ограничения или поведение, которых нет в исходном описании.
- **Адекватность приоритета:** соответствует ли назначенный приоритет важности сценария.
- **Читаемость и пригодность:** понятны ли кейсы и можно ли использовать их без существенной ручной правки.
