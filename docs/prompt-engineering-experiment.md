# Эксперимент по проектированию промпта

## Цель

Проверить, как последовательное добавление практик промпт-инжиниринга влияет на время генерации, число токенов и качество тест-кейсов. На каждом шаге меняется только промпт; модель, набор требований, температура, ограничение числа кейсов и Pydantic-схема остаются неизменными.

## Условия эксперимента

- Модель: локальная `qwen2.5:7b` через Ollama и OpenAI-совместимый API.
- Проверочный набор: те же 12 синтетических требований с эталонными сценариями, что и в предыдущем задании.
- Температура: `0.2`.
- Максимум тест-кейсов на требование: `5`.
- Формат: Pydantic `TestCaseList`, передаваемый через `response_format`.
- Внешний платный API в эксперименте не используется.

Ollama возвращает число входных и выходных токенов в usage. Для локальных вызовов нет тарификации за токен, поэтому прямая стоимость API-вызовов равна 0; энергопотребление компьютера не рассчитывается. Результаты замера времени относятся только к этому компьютеру и данной локальной установке.

## Последовательность вариантов

Варианты кумулятивны: каждый следующий сохраняет предыдущие практики и добавляет одну новую.

| Шаг | Добавляемая практика |
|---:|---|
| 0 | Baseline: исходный промпт из `build_prompt` в приложении |
| 1 | Явная цель и задача |
| 2 | Конкретные проверяемые инструкции вместо общих формулировок |
| 3 | Роль опытного QA-инженера |
| 4 | Контекст QA Copilot и запрет считать неизвестные правила подтверждёнными |
| 5 | Структурированный блок входных данных |
| 6 | Явное описание полей ожидаемого ответа в дополнение к Pydantic-схеме |
| 7 | Разделители для инструкций, контекста и входных данных |
| 8 | Декомпозиция: определить отдельные сценарии, затем сформировать по кейсу на сценарий |

Текст каждого фактически отправленного промпта сохраняется в CSV. На шаге 0 промпт проверяется на точное совпадение с текущим `build_prompt`, чтобы baseline соответствовал рабочей версии приложения.

## Метрики и оценка качества

- **Скорость:** время от начала до получения и разбора ответа, секунды.
- **Стоимость/объём:** входные, выходные и суммарные токены из ответа API. Для выбранного локального провайдера прямой денежный расход на запрос равен 0.
- **Валидность схемы:** автоматическая проверка ответа по `TestCaseList`; фиксируется доля ответов, прошедших Pydantic-валидацию.
- **Покрытие:** экспертное сопоставление с эталонными сценариями из набора по шкале из [критериев оценки](kriterii-otsenki-ai-sistemy.md).
- **Отсутствие неподтверждённых деталей:** экспертное сопоставление кейсов с исходным требованием по шкале из критериев оценки.

Содержательные оценки требуют семантического суждения; автоматическую валидность схемы нельзя трактовать как доказательство качества содержания. При ручной оценке фиксируются причины существенных пропусков или неподтверждённых предположений.

## Воспроизводимость

Эксперимент запускается из корня проекта:

```bash
source .venv/bin/activate
LLM_BASE_URL=http://localhost:11434/v1 \
LLM_API_KEY=ollama \
LLM_MODEL=qwen2.5:7b \
python -m scripts.run_prompt_experiment \
  --model qwen2.5:7b \
  --output evaluation/prompt-experiment-results.csv
```

Скрипт сохраняет каждую завершённую пару «вариант промпта / требование» сразу, поэтому прерванный прогон можно продолжить повторным запуском с тем же файлом результатов.

## Результаты прогона

Выполнено 108 запросов: 9 вариантов промпта × 12 требований. Для каждого шага использовались те же 12 требований и одна и та же модель. Все 108 ответов прошли Pydantic-валидацию.

За весь эксперимент модель обработала 124 144 токена. На шаге 8 среднее общее число токенов на запрос выросло на 84,4% относительно baseline; среднее время — на 56,8%. Рост токенов в основном пришёлся на входной промпт: среднее число входных токенов увеличилось с 182 до 772. Среднее число выходных токенов выросло умеренно — с 594 до 658.

Поскольку использовался локальный Ollama, стоимость API-запросов равна 0; электричество и амортизация оборудования не учитывались. Денежную цену для внешнего провайдера по этим данным не рассчитывали.

## Выборочная оценка качества

Для семантической проверки выбраны четыре требования из общего набора: `QA-001` (сброс пароля, простое), `QA-004` (порог бесплатной доставки, среднее), `QA-008` (права ролей, сложное) и `QA-012` (бонусные баллы, сложное). ## Наблюдения

- Все варианты сохранили 100% валидность схемы. В текущем приложении структурированный вывод уже enforced через `response_format=TestCaseList`, поэтому добавление описания полей в промпт на шаге 6 не увеличило формальную валидность.
- Самый заметный прирост на выборке по точности дал шаг 5 со структурированным входом: средняя оценка выбранных примеров выросла до 4,0. При этом покрытие не улучшилось относительно шагов 3–4, а средний расход вырос до 1 245 токенов и 57,3 секунды.
- Эффект добавления практик не был монотонным: явная цель на шаге 1 совпала с падением покрытия на выборке; роль QA-инженера и разделители сами по себе не дали устойчивого прироста; финальная декомпозиция на шаге 8 не превзошла baseline по выборочной оценке качества.
- В `QA-004` шаг 1 добавил скидки и акции, которых нет в требовании. В `QA-012` несколько вариантов придумывали курс обмена рублей на бонусные баллы или неверные числовые результаты. В `QA-008` часть вариантов пропускала ограничения роли «просмотрщик» или запрет менять чужие комментарии.
- Каждый вариант измерен одним последовательным прогоном при температуре 0,2. Поэтому небольшие различия качества и времени могут зависеть от случайности генерации, порядка запусков и состояния локальной модели.

## Вывод

Добавление инструкций, контекста и подробного формата увеличивает входные токены и в целом время ответа. В этом эксперименте оно не обеспечило стабильного роста покрытия. Структурированный вход показал лучший выборочный балл точности, но итоговый шаг с декомпозицией не дал дополнительного измеримого улучшения. Это основание для дальнейшей ручной проверки, а не доказательство универсального превосходства одной версии промпта.
